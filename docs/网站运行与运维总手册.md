# IAP-LACS 网站运行与运维总手册

> 适用网站：`https://iaplacs.xyz`
>
> 维护对象：宁夏、上饶、云南机场预报服务，以及机场预报评分服务
> 本文档更新时间：2026-08-01（CST）

本文是整站的入口运维文档。它说明网站如何从 WRF 输出变成网页图件，代码分别在哪里运行，寰/IAP、`server02`、天河、OSS、GitHub Pages 和本地 Mac 分别承担什么职责，以及日常发布、恢复和排障应如何执行。

本文不记录任何私钥、密码、OSS AccessKey、GitHub Token 或 VPN 配置。此类信息只能保存在对应账号的安全位置，例如 `~/.ssh/`、`~/.iaplacs-oss.env` 或受权限控制的密码管理器中。

## 1. 一页总览

```text
WRF 模型输出（WORK_nx / WORK_yn / WORK / WORK_tc）
                |
                | 完整性检查：SUCCESS COMPLETE WRF 或稳定时间 + 文件大小 + Time 数
                v
NCL 绘制单时次图  -->  ImageMagick 生成拼图、标题、BJT 时间标签
                |
                | Pillow / ImageMagick 生成 PNG、WebP、preview WebP
                v
寰/IAP 发布器  -->  OSS 上传预报图件  -->  build_forecast_catalog.py
                |                                  |
                |                                  v
                +------------------------------> GitHub main
                                                     |
                                                     v
                                              GitHub Pages / iaplacs.xyz

天河备用链路：同样读取 WRF、绘图并提交 data/tianhe/current/，
前端比较寰与天河 catalog 的最新起报时间，自动选更晚的数据源。

机场评分：浏览器 <-> Function Compute <-> OSS iaplacs/ratings/v1/
```

网站本身不运行传统 Web 服务器：HTML、CSS、JavaScript 和 catalog JSON 位于 GitHub Pages；大量预报图默认位于 OSS。浏览器加载 `app.js` 后每两分钟刷新一次 catalog，并按当前页面、数据源、起报时次和产品加载图件。

### 2.1 数据源选择规则

四个入口页 `index.html`、`ningxia/index.html`、`shangrao/index.html`、`airpots/index.html` 均声明：

```html
data-default-source="tianhe"
data-auto-select-latest-source="true"
data-refresh-ms="120000"
```

`app.js` 会读取：

```text
寰：data/current/forecast-runs.json
天河：data/tianhe/current/forecast-runs.json
```

开启 `data-auto-select-latest-source="true"` 时，前端比较两个 catalog 的最新起报时间，优先展示较新的一个；两个都不可用时才回退。`data-default-source` 只在两者无法比较或没有已保存选择时提供默认值。不要只改一个页面的属性，四个入口页必须保持一致。

### 3.2 浏览器缓存规则

页面使用脚本、样式版本参数，例如：

```html
<link rel="stylesheet" href="../styles.css?v=20260801-01" />
<script src="../app.js?v=20260801-01"></script>
```

每次修改 `app.js` 或 `styles.css` 后，四个入口页中引用该资源的 `v=` 值都应更新。否则 GitHub Pages 已发布但访问者浏览器仍可能使用旧脚本。catalog 请求会附加缓存参数并使用 `no-store`，但 CDN 对裸 URL 仍可能短暂缓存数分钟。

### 4.2 OSS 图件

生产图件公网基址为：

```text
https://iaplacs-forecast-images-hk.oss-cn-hongkong.aliyuncs.com/iaplacs/
```

发布器上传顺序必须是：

1. 生成 PNG、WebP、`preview.webp`；
2. 上传图件到 OSS；
3. 用公开 URL 回读并确认 `HTTP 200` 和正确 Content-Type；
4. 运行 catalog 生成器，使 JSON 引用已存在的 OSS URL；
5. 只提交 catalog/轻量元数据到 GitHub。

网页图件格式约定：

| 文件 | 用途 |
| --- | --- |
| `.png` | 原始高清图，供下载 |
| `.webp` | 放大查看或中等清晰度展示 |
| `.preview.webp` | 首屏预览，减少移动端解码压力 |
| `manifest_fragment.json` | 机场产品起报/有效时间、统计信息等元数据 |
| `airport_precip_totals.json` | 三家机场累计/峰值降水摘要 |

正常保留每个产品族最近 5 个网站时次。不要把完整 `wrfout_d01_*`、服务器图件缓存或 `data/current/maps/*` 的批量产物从 Mac 提交进仓库。

### 4.3 OSS 发布环境变量

IAP 发布脚本通常从受权限保护的 `~/.iaplacs-oss.env` 读取配置。文件不进入 Git，常见变量名称如下：

```bash

IAPLACS_OSS_BUCKET=iaplacs-forecast-images-hk
IAPLACS_OSS_ENDPOINT=<香港 OSS endpoint>
IAPLACS_OSS_PUBLIC_BASE_URL=https://iaplacs-forecast-images-hk.oss-cn-hongkong.aliyuncs.com
```

不得在文档、终端历史、Git 或网页内记录该文件中实际的身份凭据。发布器只应读取该文件，不应 `cat` 到日志。

### 5.2 完整性判断

脚本不是只看目录名，而是检查 `wrfout_d01_*` 是否适合渲染。不同产品阈值略有不同，但原则一致：

1. 文件达到产品设定的最小尺寸；宁夏区域渲染脚本默认不少于 8 GB，云南/上饶自动发布常用不少于 20 GB；
2. `ncdump -h` 可读，并且 `Time` 数不少于可绘制 T13 的数量；
3. 优先以同目录 `rsl.error.0000` 末尾出现 `SUCCESS COMPLETE WRF` 判定完成；
4. 若没有成功标记，只在文件至少 20 分钟没有变化后才允许继续；
5. 从 T13 开始绘制，跳过前 12 小时 spin-up；最长时效由实际 `Time` 数决定，不能硬编码为固定 36 张。

需要人工确认一个时次时：

```bash
cd /data1/elpt_2022_00083/zhoubj/WORK_yn/2026073100/gfs/wrf
ls -lh wrfout_d01_2026-07-31_00:00:00
tail -n 200 rsl.error.0000 | grep 'SUCCESS COMPLETE WRF'
ncdump -h wrfout_d01_2026-07-31_00:00:00 | grep 'Time = UNLIMITED'
```

未满足条件时等待下一轮自动检查，不要手工复制正在增长的文件，也不要手工强制发布半成品。
唯一例外是下述受控的北京时间 06 时早间快照任务。

### 5.2.1 降水累计分量

宁夏、上饶、云南机场的运行产品保留原有的 `RAINNC + RAINC` 雨量基线；当 WRF 文件包含
`GRAUPELNC`、`HAILNC` 时，自动将两项冰相累计量加入逐小时和 12/24 小时累计结果。该处理与
`_00_DESKTOP/00_TMP/TF` 的冰相降水约定一致，旧文件缺少这些变量时会自动回退为原有雨量计算，
无需修改网页或补造变量。机场点值和降水精简 NetCDF 备份使用同一规则，并在 JSON/NetCDF 元数据中
记录实际参与计算的变量。

四个服务的独立“冰雹预警”产品只计算 `GRAUPELNC + HAILNC`，不混入 `RAINNC/RAINC`。冰雹预警
使用与同服务“中国×部”逐小时降水完全相同的大区域画布、省界和经纬度范围：宁夏对应中国中部、
上饶对应中国东南部、云南机场对应中国西南部、新疆对应中国西部；区域按钮仅代表网页产品名称，
不再把冰雹结果裁切到宁夏、上饶、云南或新疆的小区域。该规则由
`rain_worknx_national_hour_bjt.ncl` 和各服务发布脚本共同保证，后续自动起报继续遵循同一逻辑。

冰雹预警色标与普通逐小时降水分开，固定边界为
`0、0.01、0.05、0.10、0.25、0.50、1.00 mm`，超过 `1 mm` 的值共用最高色阶。`GRAUPELNC`
和 `HAILNC` 是毫米单位的累计模式量（参见 [WRF User's Guide](https://www2.mmm.ucar.edu/wrf/users/docs/user_guide_v4/v4.3/users_guide_chap5.html)），逐小时图使用相邻时刻差值。这套非等距分级用于
在 `0.01–1.00 mm` 范围内区分弱冰相信号，不是中央气象台或地方气象部门的法定冰雹
预警标准，也不应解读为冰雹直径。

### 5.2.2 北京时间 06 时早间快照

UTC 06 起报对应北京时间 14 时起报。它有时到次日清晨仍未完成，但早班预报员需要在北京时间
06 时制作早报。运行时因此使用 `publish_bjt06_partial_forecasts.sh` 对“上一日 UTC 06”起报执行
一次受控的提前发布。该流程先用 `ncks` 固定当前可读的 `Time` 范围，只提取
`Times、XLAT、XLONG、RAINNC、RAINC`，以及存在时的 `GRAUPELNC、HAILNC`，不会让绘图器直接
反复读取正在增长的 20-40 GB `wrfout`。

一致性快照保存在：

```text
/data1/elpt_2022_00083/kerui/Website/.partial_snapshots/<service>/<YYYYMMDD06>/gfs/wrf/
```

该目录不进入 Git，也不进入每日运行时备份；每个服务只保留最近 2 个快照。发布成功后，小型状态
文件写入 `state/bjt06_partial/`，记录 `partial/complete`、原始源路径、文件大小、修改时间、Time
数量和发布时间。宁夏、云南、新疆由各自标准发布器绘制，上饶仍提交 Slurm；图件继续通过 server02
上传 OSS 并更新 GitHub catalog。

06:00、06:15、06:30、06:45 和 07 时同样的四个时刻会重试，原因是精确到 06:00 时某个服务
可能尚无 T13。某服务一旦发布过半成品，后续重试不会反复发布增长中的文件；只有检测到同一起报
已经出现 `SUCCESS COMPLETE WRF` 时，才会在重试窗口内立即覆盖为完整结果。

完整结果还有三重兜底：云南状态保存“路径、大小、修改时间、Time 数、完成标志”的完整源签名；
上饶 pipeline 保存同一起报的源状态；每小时第 5 分钟巡检按完整 WRF 的 Time 数计算期望逐时图数
`min(Time - 13, 36)`。完整源图数高于早间半成品时，会清理该起报旧图、重画并重新上传。各服务
发布器使用独立 `flock`，禁止半成品和完整结果同时清理一个输出目录。

人工只读检查：

```bash
TARGET_RUN=2026080406 tools/publish_bjt06_partial_forecasts.sh --dry-run
cat state/bjt06_partial/ningxia-2026080406.state
tail -n 200 logs/bjt06-partial.log
```

不要删除当天状态来强制重跑。确需人工重跑时，先确认同服务没有发布进程或 Slurm 作业，并保存
状态文件和日志。

### 5.4 SHP 输入

```text
SHP/yunnan_city.*
```

缺少同名 `.shp`、`.shx`、`.dbf`、`.prj` 中任一关键文件时，NCL 可能不画边界或直接失败。云南只绘制市级边界；宁夏、上饶使用相应的市县边界。宁夏县界于 2026-08-10 按阿里云 DataV 行政区划接口的五个地级市完整边界更新，必须包含 22 个现行县级单元，并分别包含 `640303 红寺堡区` 和 `640324 同心县`；旧版 21 单元数据会把红寺堡并入同心县，不能继续使用。调整边界线、投影或色标后必须从完整 WRF 重新绘制，不应后期替换历史图片。

## 7. server02：GitHub 与中央气象台实况中继

IAP 计算节点的网络/库环境不一定可直连 GitHub。`server02` 作为稳定中继：接收 IAP 图件/元数据、拉取或更新 Git checkout、将图件上传 OSS、提交 catalog；中央气象台 24 小时降水实况也可在这里抓取与发布。

### 7.1 Git 运行环境

`server02` 的 Intel/Conda 环境可能注入不兼容的 `LD_LIBRARY_PATH`，导致 Git、SSH 或 `ssh-keygen` 的 OpenSSL/Intel 动态库错误。Git 命令使用系统二进制并清理相关环境变量：

```bash
env -u LD_LIBRARY_PATH -u LD_PRELOAD \
  GIT_SSH="$HOME/.ssh/git-iaplacs-ssh" \
  /usr/bin/git <command>
```

该服务器旧 Git 只支持 `GIT_SSH`，不使用 `GIT_SSH_COMMAND`。

所有 server02 发布器共享 `$HOME/.iaplacs-github-publish.lock`。锁必须覆盖 Git pull、图件
落盘、OSS 上传、catalog 生成、commit 和 push 的完整过程，避免中央台实况与三类预报并发写入同一
checkout。若出现 `.git/index.lock`，先确认没有 Git、OSS 或发布进程；将锁文件移入
`~/iaplacs-publish-recovery/` 留档后，再提交/同步遗留 catalog，不能直接在运行中的任务里删除锁。

### 7.2 Deploy Key 配置

## 9. 自动发布的完整顺序

无论寰/IAP 还是天河，正确顺序都相同：

1. **发现时次**：找 `wrfout_d01_*`；
2. **判定完整**：检查 `rsl.error.0000`、文件稳定时间、大小与 Time；
3. **绘制单图**：NCL 读取 WRF、SHP、色标、机场经纬度；
4. **生成组合图**：ImageMagick 为每格加 BJT 时间、拼接 6 列网格、添加起报时间；
5. **累计降水**：仅保留跳过 spin-up 后满足 BJT 对齐的 12/24 小时完整窗；
6. **提取机场统计**：云南运行 `extract_yunnan_airport_precip.py`，产生 `airport_precip_totals.json`；
7. **Web 优化**：生成高质量 WebP 与 `preview.webp`；
8. **上传 OSS**：上传所有必需资源并回读；
9. **重建 catalog**：运行 `build_forecast_catalog.py` 或天河专用生成器；
10. **Git 发布**：仅提交 catalog 和设计上需要进入 Pages 的轻量文件；
11. **在线核验**：检查页面 catalog、图件 URL、原图下载、服务标签和最新时次；
12. **保留/备份**：按产品保留 5 个网站时次，按策略维护运行时/NetCDF 备份。

前 8 步任一步失败，都不应更新 catalog。否则网页会出现新时次但图件 404，或展示混合时次的统计。

## 10. Git 操作纪律

本仓库有 IAP/天河自动发布器，人工修改代码时可能与自动 catalog 提交并发。推荐顺序：

```bash
cd /Users/xiaoxiaotu/_01_IAP/Website
git status -sb
git add <明确修改的文件>
git diff --cached --check
git commit -m "说明本次修改"
git pull --rebase origin main
git push origin main
```

规则：

1. 不使用 `git add .`，避免将图片缓存、`.tmp`、大型 NetCDF、日志或未知文件提交；
2. 发布器自动提交数据时，人工代码提交必须先 `pull --rebase`；
3. 发现他人/自动任务的未提交改动时，不回退、不清空，先理解来源；
4. 不使用 `git reset --hard` 或 `git checkout --` 清理生产文件；
5. `Codex_resume_iaplacs_website.md`、运行时 ZIP、缓存目录均由 `.gitignore` 排除。

1. 宁夏、上饶、机场三个服务都能打开；
2. 数据源按钮的高亮与实际最新 catalog 一致；
3. 区域和中国中部/东南部/西南部两个标签都有图；
4. 逐时、拼图、12 小时累计、24 小时累计的有效时间符合 BJT；
5. 原图下载返回 PNG 而不是 404；
6. 云南机场摘要与图件时次一致；
7. 机场评分显示“评分自动存档”。

### 每周

1. 检查 IAP 运行时备份是否按天生成且能通过 `sha256sum -c`；
2. 检查 OSS 保留时次数量和评分目录增长；
3. 检查 `server02` Deploy Key 仍能 `ssh -T git@github.com`；
4. 在天河执行 `tools/tianhe_publish_forecast_to_github.sh --dry-run`，确保备用链路仍可接管；
5. 检查 GitHub Pages 自定义域名和 HTTPS 状态。

## 13. 故障快速定位

| 现象 | 优先检查 | 正确处理 |
| --- | --- | --- |
| 新 WRF 已出现，网页无新时次 | WRF 是否成功/稳定、发布 cron 日志、状态文件 | 等待完整；必要时先 `--dry-run` 再手工发布 |
| 网页有新时次但图片 404 | OSS 是否已经上传、catalog URL、对象 ACL/Content-Type | 重新上传并回读后再重建 catalog |
| 图件颜色、边界或字体不对 | 实际使用的 NCL/SHP/渲染脚本版本 | 从 WRF 重绘，不要只修改最终 WebP |
| 页面选到了错误数据源 | 两个 catalog 的最新时间、入口页 `data-*` 属性、浏览器缓存 | 修复 catalog/属性，递增 JS/CSS 版本并强制刷新 |
| IAP 无法 Git push | `server02` 连通、Deploy Key、`LD_LIBRARY_PATH` 污染 | 通过 `server02` 系统 Git 中继，不在网页写 Token |
| 天河 Git HTTPS 报 `libssh`/OpenSSL 错 | Conda/Spack 库污染 | 用 `tools/tianhe_system_git.sh` 或清理 LD 变量 |
| 天河无法解析 GitHub | DNS/代理/VPN、HTTPS/SSH 路径 | 优先 HTTPS + 系统 Git；不要修改系统 DNS 或安装无验证二进制 |
| 机场评分无计数/无法写入 | FC 日志、RAM 角色/策略、HTTP trigger、CORS | 按评分服务文档逐层验证 GET、OPTIONS、POST |
| 空间紧张 | 网站缓存、运行时备份、已验证的精简 NetCDF | 先确认备份，再按保留策略处理；默认不删完整 WRF |

## 14. 恢复顺序

### IAP 停机但天河可用

1. 在天河检查 `bashrc`、Conda NCL、ImageMagick、Git 和模型目录；
2. 进入隐藏 checkout，执行 `tools/tianhe_publish_forecast_to_github.sh --dry-run`；
3. 验证三类 WRF 完整、Git 能推送、`data/tianhe/current/forecast-runs.json` 能生成；
4. 再安装或恢复天河 cron；
5. 前端因 `data-auto-select-latest-source` 会选择更新的天河 catalog。

### 天河不可用但 IAP 可用

1. 在 IAP 运行目录确认脚本、SHP、OSS 环境、`server02` Deploy Key；
2. 检查 `crontab -l`，只恢复受 `IAPLACS` 标记管理的任务；
3. 先运行一个服务的 `--dry-run`；
4. 成功后依次补发宁夏、云南、上饶和必要的 CMA 实况；
5. 回读 OSS 和在线 catalog 后，页面会自动选较新的寰数据。

### 运行时脚本丢失或服务器重启

1. 从 `backups/runtime/iaplacs-runtime-*.tar.gz` 选择最新校验通过的归档；
2. 查看归档中的 `runtime-paths.txt`、`crontab.txt`、`git-state.txt`，先确认恢复目标；
3. 只恢复脚本、NCL、SHP、状态和 cron；不覆盖 `zhoubj/WORK*`、SSH 密钥或 OSS 凭证；
4. 重新部署后先 `--dry-run`，再恢复 cron。
